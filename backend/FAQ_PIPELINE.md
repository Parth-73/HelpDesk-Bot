# FAQ extraction and local semantic retrieval

The chatbot now has two separate paths: an explicit offline Gemini ingestion command and a local approved-FAQ lookup between the existing exact cache and RAG. No frontend changes or public ingestion endpoints were added.

## Current live dataset

The configured PostgreSQL database has 23 active FAQs generated by Gemini and checked against the official documents. Four of the 27 candidates were rejected. Review decisions explicitly identify the reviewer as a Codex AI agent, not a human. Generated answers were not rewritten; two misleading paraphrases were removed, and generated threshold questions were connected to the full existing AND-condition answer. Raw Gemini results remain preserved in `faq_batches`.

See `artifacts/faq_candidates/faq_dataset.json`, `review_decisions.json`, `curation_decisions.json`, `extraction_report.json`, `semantic_index.json` and `live_verification.json`. The live report records seven actual extraction request attempts: four schema-rejected requests during diagnosis followed by three successful batches. Offline calls remain separate from runtime metrics. A real chat-contract verification returned the stored passing-policy answer with zero runtime Gemini generation attempts, and its repeat was cached.

The normal chat service automatically loads this active database index. Restart an older backend process once to load the latest code; active-pointer refresh then occurs within the configured refresh interval. No regeneration is needed to use the stored FAQs.

## 1. Prepare the shared database and CPU model

From `backend/` with the existing Python 3.12 environment active:

```sh
pip install -r requirements.txt
python -m app.init_db
python -m app.scripts.prepare_faq_model
```

The additive schema initialization registers the FAQ tables without changing the original documents or resetting chat counters. Model preparation downloads the pinned `sentence-transformers/all-MiniLM-L6-v2` quantized ONNX graph and tokenizer, recording hashes in `model_assets/minilm/manifest.json`. That directory is ignored by Git. Runtime does not download models or call an embedding API. The production inference path uses ONNX Runtime CPU, tokenizers, NumPy and one bounded worker; it does not import PyTorch or Sentence Transformers. Include the prepared assets in your deployment build (see deployment below).

## 2. Inspect without API quota

```sh
python -m app.scripts.generate_faqs --dry-run
```

This hashes all originals, resolves current authority and writes `artifacts/faq_candidates/extraction_report.json` plus an explicitly empty dry-run dataset. It makes no Gemini calls or database writes. Running without `--enable-live` also defaults to dry-run. A configured API key alone never enables generation.

## 3. Explicitly generate candidates

```sh
python -m app.scripts.generate_faqs --enable-live
```

This consumes Gemini quota and uses your existing backend key, model, timeouts and retries. It reuses the existing Gemini client implementation rather than introducing a second integration. Three related source batches cover course information, assessment policies and examination policies. The model discovers questions and paraphrases from the evidence; there are no production question lists/templates. Coverage guidance includes factual, conditional, exception, eligibility, comparison and supported calculation questions.

Gemini receives a simplified supported schema, while all size, type and extra-field constraints remain enforced by strict local Pydantic validation. Offline extraction uses `FAQ_EXTRACTION_TIMEOUT_SECONDS` (default 60), independently of the shorter student-question timeout.

Results are persisted after every successful batch. Rerunning unchanged documents/prompt/model resumes failed batches or returns the existing dataset without another generation. `--enable-live --force` creates a new immutable candidate snapshot while preserving the active one. Use one extraction process; a PostgreSQL transaction advisory lock prevents simultaneous extraction of the same snapshot. The offline process temporarily holds a database connection for this lock, so do not run large numbers of ingestions concurrently.

Artifacts include `faq_dataset.json`, `extraction_report.json` and `review_template.json`. Reports contain actual batch attempt totals, deduplication counts, validation status counts, hashes and prompt/model versions. Offline attempt counters live in `faq_batches.extraction_calls`; they never increment student-facing runtime Gemini statistics. Reports record attempts before SDK invocation, with the same small crash-window limitation as runtime counters.

When an unreviewed inactive snapshot needs compatibility revalidation, run `python -m app.scripts.revalidate_faqs --snapshot SNAPSHOT_ID`. It makes no Gemini calls, preserves raw batch results and refuses to change reviewed or active content. Filename-only source references are resolved only when exact complete evidence identifies a unique authoritative passage; fabricated filenames and partial quotes are still rejected. The known course identifier DPM-101 is treated as a name rather than an unsupported new numeric threshold.

## 4. Review before approval

Every structurally valid candidate starts as `needs_review`. Fabricated IDs/quotes, superseded sources, omitted passing conditions, unsupported numbers and obvious restriction reversals are rejected. Exact quotation matching alone never produces `approved` status. A reviewer must check that the answer addresses the question, preserves AND/OR, minimum/maximum, allowed/prohibited, overall/final scope, current/historical policy and every paraphrase. Calculations need particular scrutiny; new numerical claims in factual answers are rejected, while explicitly tagged calculations require manual arithmetic and entailment review before approval.

Copy `review_template.json` to a separate `review_decisions.json`. For each reviewed item, set `decision` to `approved` or `rejected`, and fill `reviewer` and a meaningful `rationale`. Keep `faq_id`, `content_hash` and `snapshot_id` unchanged. `REVIEW_REQUIRED` is intentionally not a valid approval decision. You can submit a subset; unreviewed candidates remain unavailable. Context-dependent candidates cannot be approved for direct deterministic matching; standalone equivalents should be generated/reviewed instead.

```sh
python -m app.scripts.review_faqs --review review_decisions.json
python -m app.scripts.generate_faqs --report --snapshot SNAPSHOT_ID
```

Reviews are tied to immutable content hashes. Changing the answer/paraphrases invalidates the review. Active snapshots cannot be edited or reviewed in place.

## 5. Calibrate and activate an index

Create a reviewer-labeled `calibration.json` array. Each object contains:

```json
{
  "question": "A reviewer-selected test question",
  "expected_faq_id": "UUID of the correct approved FAQ, or null for no match",
  "category": "paraphrase"
}
```

Use JSON `null`, not a string, for no match. Supply at least eight cases, including positive held-out paraphrases and hard negatives. Required categories are `paraphrase`, `scope`, `negation`, `conditional`, `historical`, `off_topic`, and `ambiguous`. Include near-neighbor overall/final thresholds, numerical scenarios with different scores, old policies and unrelated questions. Do not rely only on paraphrases already stored in the index. FAQ IDs must come from the approved dataset.

```sh
python -m app.scripts.review_faqs --snapshot SNAPSHOT_ID --activate --calibration calibration.json
```

The command precomputes normalized embeddings for canonical questions and approved paraphrases, searches empirical score/margin operating points with zero false accepts on the reviewed cases, and fails if no useful safe point exists. The margin compares different FAQ IDs, not two paraphrases of the same FAQ. Cosine similarity is not a probability. These calibration results apply to the provided cases; evaluate a separate held-out set before claiming wider accuracy.

It validates all source/review hashes again and commits the compressed embedding payload plus active-snapshot pointer atomically in PostgreSQL. `artifacts/faq_candidates/semantic_index.json` is an export; PostgreSQL remains authoritative. A failed replacement leaves the old approved index intact. Runtime workers refresh the active pointer within `FAQ_REFRESH_SECONDS` (default 30). New response-cache keys include the active FAQ snapshot ID, preventing earlier RAG abstentions or responses from masking an updated FAQ snapshot.

## Online behavior

1. Load recent student context and determine whether the question depends on it.
2. Check the existing exact response cache, now scoped to the active FAQ snapshot.
3. Match approved canonical/paraphrase formulations locally, or encode the query once with the reused ONNX session and compare against precomputed vectors.
4. Require compatible numeric scenarios, negation, assessment scope and historical/current qualifiers, plus calibrated score and top-two margin.
5. Return the reviewed answer with original source filenames only for a reliable match; otherwise use existing source retrieval and Gemini RAG.

Local context resolution handles a passing-policy follow-up about the final exam by combining the previous subject with the current question. Other ambiguous dependent turns go to the existing context-aware RAG pipeline; no extra model call is used just to rewrite questions. Conservative guards can reduce FAQ hit rate, especially for unfamiliar wording; correctness has priority.

Internally, answers distinguish `semantic_faq`, `gemini`, `abstention` and `exact_cache` origins. The API contract is unchanged. A first semantic FAQ answer is **not** marked cached and does not increment cache hits or Gemini calls. Its later exact response-cache hit does increment cache hits. Shared same-key generation retains the existing documented cache semantics. Student question totals and idempotency remain unchanged.

If model assets are absent, inference fails, or the measured process RSS exceeds `FAQ_MEMORY_LIMIT_MB`, the service logs an explicit fallback mode: approved exact formulations remain available, and unmatched questions use RAG. A missing/stale/invalid approved dataset uses RAG entirely. This does not fabricate FAQ availability. No model is loaded at all until an active approved dataset exists. `/api/ready` includes `faq_mode` for visibility; `not_checked` means no request has loaded the optional FAQ index yet. This optional mode does not change core readiness requirements.

## Document updates and deployment

Original `.txt` files remain unchanged. Deploy/ingest an explicitly revised source snapshot, rerun extraction, review/calibrate the replacement, and restart the API to load the new document hashes. A current worker uses an immutable startup knowledge snapshot; in-place edits are not live-reloaded. Any FAQ snapshot with a different combined document hash is ineligible. Existing cache keys already include that hash, and idempotency replays from a different knowledge version return an outdated-request error.

New additive tables:

- `faq_snapshots`: immutable source/prompt/model snapshot, report and compressed precomputed index.
- `faq_batches`: resumable related-passage extraction results and offline SDK attempt counts.
- `faq_entries`: candidates, paraphrases, exact evidence, source IDs, validation notes, content hashes and explicit review decisions. Unique snapshot/question hashes prevent rerun duplicates.
- `faq_catalog`: singleton active-snapshot pointer.

No vector database, redundant chat cache or second usage-statistics table is introduced. Embeddings persist in PostgreSQL as compressed float32 vectors plus JSON metadata; NumPy arrays are reused in memory. Never enable automatic live extraction in a web-service startup command.

For Render, install requirements and prepare model assets in the build command, using the pinned revision. Initialize the additive schema as already documented. Run the extraction/review/activation commands privately against the intended database; local files are exports rather than runtime dependencies. The model binary is not tracked in Git and Render runtime disk need not be persistent.

## Tests and measurements

```sh
# Use an isolated PostgreSQL test database; no live Gemini key is used by tests.
python -m pytest -q
python -m app.scripts.measure_faq_resources --queries artifacts/resource_queries.json --output artifacts/faq_resource_report.json
```

Mocked extraction examples are confined to `tests/faq_examples.py`; they are not a production FAQ dataset or generator. The manual `tests/test_db.py` diagnostic is guarded so Pytest import cannot connect to your configured Supabase account.

The resource report records observed RSS and CPU inference latency on this machine, with a clear standalone-process scope. It does not prove a full application will fit every 512 MB host or establish multi-user capacity. Validate the whole deployed service under representative traffic.
